# قرارداد KPI داشبورد روزانه

این سند قرارداد مصرف KPIهای عملیاتی در داشبورد روزانه آموزشگاه موسیقی فاتح است.

## منبع حقیقت

APIهای داشبورد روزانه باید تعدادهای یکتا را در `metrics` برگردانند. UI نباید برای KPIهای یکتا با `flatMap(session.students)` دوباره شمارش انجام دهد.

## KPIهای یکتا

| فیلد | معنی |
|---|---|
| `unique_students` | تعداد هنرجویان یکتا در جلسات فعال روز، بر اساس `studentId` |
| `unique_present_students` | تعداد همان هنرجویان یکتا که حداقل یک وضعیت `present` در جلسات فعال روز دارند |
| `unique_pending_students` | تعداد هنرجویان یکتا که حداقل یک وضعیت `pending` در جلسات فعال روز دارند |

جلسات `cancelled` نباید در این KPIها اثر داشته باشند.

## KPIهای مالی

KPIهای مالی باید از وضعیت مالی محاسبه‌شده در Backend استفاده کنند و UI نباید تاریخ سررسید، معوقه یا مانده را دوباره محاسبه کند.

## شمارش عملیاتی

برخی شمارش‌ها ذاتاً row-based هستند و یکتا نیستند؛ مانند تعداد موارد اقدام یا تعداد enrollment-sessionهایی که حضورشان ثبت نشده است. این شمارش‌ها باید با نام و برچسب UI شفاف باشند و با KPI «هنرجوی یکتا» مخلوط نشوند.

## قرارداد UI

- «هنرجوی امروز» = `metrics.unique_students`
- «حضور» = `metrics.unique_present_students / metrics.unique_students`
- «در انتظار» = `metrics.unique_pending_students`
- تغییر فیلتر مدرس نباید منبع حقیقت KPI روزانه را به شمارش تصادفی کارت‌های DOM تبدیل کند.
- اگر `metrics` در پاسخ API وجود نداشت، UI باید fallback مشخص داشته باشد یا وضعیت unavailable را نشان دهد؛ نباید silently یک شمارش متفاوت را به عنوان KPI authoritative معرفی کند.

## مرحله بعد

پس از این قرارداد، `daily-dashboard.js` باید مصرف مستقیم `metrics` را انجام دهد. سپس `timelineRange()` از بازه ثابت `16:00–22:00` خارج و بر اساس اولین/آخرین جلسه روز محاسبه می‌شود.
