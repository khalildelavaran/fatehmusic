# داشبورد روزانه — Phase 1 Implementation

## هدف
اجرای فاز ۱ معماری مرکز عملیات روزانه بدون تغییر دادن مدل دامنه اصلی و بدون حذف کنترل فعلی داشبورد.

## موارد پیاده‌سازی‌شده

### Action Center
`daily-command-center.api.ts` شاخص‌های عملیاتی لازم را فراهم می‌کند و ماژول `daily-command-center.js` آن‌ها را به بخش «نیازمند اقدام» تبدیل می‌کند:
- حضور هنرجوی ثبت‌نشده
- حضور مدرس ثبت‌نشده
- جلسه بدون اتاق
- تداخل مدرس
- تداخل اتاق
- ترم دارای معوقه
- پرداخت ناقص
- موارد نزدیک تمدید

برای موارد قابل اتصال به جلسه، Action Center شناسه دقیق جلسه‌ها را از Backend دریافت می‌کند و با کلیک روی هر مورد همان Session Cardها را در داشبورد فوکوس می‌کند.

### KPI مالی
- پرداخت‌های ثبت‌شده در تاریخ انتخاب‌شده
- تعداد تراکنش‌های روز
- تعداد ترم‌های دارای مانده
- تعداد ترم‌های دارای معوقه
- تعداد ترم‌های دارای پرداخت ناقص

«بدهی باز» و «معوقه» دو مفهوم جدا هستند؛ بدهی باز شامل مانده‌های پرداخت‌نشده است و معوقه فقط مواردی است که تاریخ سررسید آن‌ها گذشته است.

### KPI تمدید
تعداد ترم‌های فعال که ماهانه هستند یا طبق قاعده فعلی حداکثر یک جلسه مصرف‌نشده دارند.

### KPI هنرجوی یکتا
شمارش «هنرجوی امروز» بر اساس `studentId` انجام می‌شود، نه `enrollmentId`. بنابراین اگر یک هنرجو در چند Session روز حضور داشته باشد، در KPI هنرجو فقط یک‌بار شمرده می‌شود.

### وضعیت استاد
برای هر مدرس:
- تعداد جلسات
- بازه زمانی اولین تا آخرین جلسه
- تعداد حضور ثبت‌نشده
- تعداد غیبت
- وضعیت تکمیل حضور

### Conflict
منطق Phase 1 دو نوع تداخل را مستقل می‌سنجد:
- تداخل زمانی مدرس
- تداخل زمانی اتاق

این عمداً جایگزین مفهوم قبلی «تداخل هم‌زمان مدرس و اتاق» است.

### Quick Search
جستجوی سریع Backend برای:
- هنرجو
- مدرس
- کلاس

نتایج محدود به ۲۰ مورد هستند و جستجو با LIKE و escape کردن wildcardها انجام می‌شود. نتایج جلسه‌های مرتبط را با شناسه دقیق Session برمی‌گردانند تا Navigation روی همان Sessionهای روز انجام شود.

## اتصال به صفحه اصلی
ماژول Command Center روی کنترلر اصلی داشبورد سوار می‌شود و Session Cardهای موجود را به‌عنوان target عملیاتی استفاده می‌کند. کنترلر اصلی همچنان منبع state و عملیات Session است؛ Command Center نباید state موازی برای Sessionها ایجاد کند.

## تصمیم معماری
ماژول Phase 1 از API مرکز عملیات داده می‌گیرد و برای جلوگیری از دستکاری مستقیم DOM کنترلر اصلی طراحی شده است. در ادامه باید presentation layer در همان Single Controller / Single State ادغام شود تا دو state مستقل نداشته باشیم.

## موارد بعدی قبل از merge
1. نمایش جزئیات مالی روی Session Card: مبلغ صورتحساب، پرداخت‌شده، مانده، سررسید و وضعیت.
2. تکمیل workflow مستقل تمدید، بدون مخلوط شدن با وضعیت پرداخت.
3. تفکیک دقیق «تمدید»، «پایان ترم»، «پرداخت» و «جلسه جبرانی» در عملیات روزانه.
4. افزودن NOW line به Timeline کنترلر اصلی در صورت نیاز به ادغام کامل presentation layer.
5. اجرای build/typecheck و تست D1 روی داده واقعی.
6. اصلاح timezone به‌عنوان بخشی از قرارداد روز مدرسه.
7. حذف materialization از GET داشبورد در مرحله معماری بعدی و انتقال آن به mutation/job صریح.
8. جایگزینی queryهای N+1 دانش‌آموز با خواندن set-based در API داشبورد.
