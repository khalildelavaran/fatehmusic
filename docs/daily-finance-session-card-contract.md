# قرارداد مالی کارت جلسه در داشبورد روزانه

## هدف

کارت هر هنرجو در داشبورد روزانه باید وضعیت مالی همان ترم را در کنار عملیات حضور نشان دهد؛ بدون ایجاد منطق مالی مستقل در UI.

## منبع حقیقت

منطق وضعیت مالی باید از `src/server/finance-calculations.ts` و خروجی API روزانه تغذیه شود. UI نباید وضعیت `paid`، `partial`، `overdue` یا مانده را دوباره محاسبه کند.

## داده‌های مورد نیاز کارت

برای هر enrollment session:

- `invoiceId`: شناسه صورتحساب جاری، در صورت وجود
- `invoiceAmount`: مبلغ کل صورتحساب
- `paidAmount`: مجموع پرداخت‌های ثبت‌شده برای صورتحساب
- `balance`: مانده کل صورتحساب
- `amountDueToDate`: مبلغی که بر اساس جلسات مصرف‌شده تا امروز سررسید عملیاتی شده است
- `balanceToDate`: مانده قابل مطالبه تا امروز بر مبنای جلسات مصرف‌شده
- `tuitionDueDate`: تاریخ سررسید
- `financialStatus`: یکی از `none`, `pending`, `partial`, `paid`, `overdue`
- `overdue`: آیا صورتحساب از تاریخ سررسید گذشته و هنوز مانده دارد
- `nearDue`: آیا در بازه نزدیک به سررسید قرار دارد
- `unpaidSessions`: تعداد جلسات بدون پوشش پرداخت بر اساس محاسبه مالی

## رفتار UI

کارت باید به‌صورت فشرده این موارد را نشان دهد:

1. وضعیت مالی
2. مبلغ کل
3. پرداخت‌شده
4. مانده
5. تاریخ سررسید، وقتی موجود است
6. عملیات `ثبت پرداخت` وقتی مانده وجود دارد
7. پیام واضح برای نبود صورتحساب
8. تمدید ترم به‌عنوان workflow مستقل از پرداخت

## پرداخت سریع

دکمه پرداخت باید از endpoint موجود پرداخت استفاده کند و پس از موفقیت داده‌های داشبورد را دوباره دریافت کند. فرم پرداخت نباید موجودی یا وضعیت مالی را در مرورگر محاسبه و ذخیره کند.

## تفکیک مفاهیم

- **بدهی باز**: هر صورتحساب دارای مانده
- **پرداخت ناقص**: صورتحساب دارای هم پرداخت و هم مانده
- **معوق**: صورتحساب دارای مانده که تاریخ سررسید آن گذشته است
- **تسویه‌شده**: مانده صفر
- **تمدید**: ایجاد ترم/صورتحساب جدید؛ صرفاً ثبت پرداخت نیست

## نکته معماری

نام فیلدهای API و UI باید یک قرارداد مشخص داشته باشند. از aliasهای پراکنده مانند `invoiceTotal`/`invoiceAmount` یا `amountPaid`/`paidAmount` در بخش‌های مختلف جلوگیری شود. اگر سازگاری موقت لازم است، تبدیل باید فقط در `normalizeSession()` انجام شود و قالب canonical همان نام‌های API باقی بماند.

## گام بعدی

پس از تثبیت قرارداد، UI کارت باید از نام‌های canonical استفاده کند و تاریخ سررسید را نیز نمایش دهد. سپس workflow تمدید از منطق پرداخت جدا و برای هر دو سمت API و UI صریح شود.
