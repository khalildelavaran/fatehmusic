# معماری داشبورد روزانه آموزشگاه موسیقی فاتح

**وضعیت:** مرجع اجرایی توسعه داشبورد روزانه
**نسخه:** 1.0
**تاریخ:** 2026-09-17
**هدف:** تبدیل داشبورد روزانه از یک صفحه نمایش جلسات به «مرکز عملیات روزانه آموزشگاه» بدون شکستن معماری فعلی Single Controller / Single State.

## 1. اصل اصلی محصول

داشبورد باید به سؤال منشی پاسخ دهد:

> «الان چه اتفاقی در آموزشگاه می‌افتد و برای چه چیزی باید اقدام کنم؟»

بنابراین اولویت UI با **وضعیت، هشدار و اقدام** است؛ نه صرفاً نمایش داده.

## 2. معماری فعلی که حفظ می‌شود

- یک `state` مرکزی در `daily-dashboard.js`.
- رندر بر اساس state؛ بدون چند کنترلر مستقل برای یک DOM.
- Event delegation روی ریشه داشبورد.
- عدم استفاده از `MutationObserver`.
- timeline و کارت هنرجو از یک رکورد مشترک `state.sessions` استفاده می‌کنند.
- تغییر ساعت/اتاق فقط روی `class_session` همان روز اثر می‌گذارد، نه برنامه هفتگی.
- اتاق‌ها از API خوانده می‌شوند و hard-code نمی‌شوند.
- اعتبارسنجی نهایی تغییرات در Backend انجام می‌شود.
- پیشنهاد هوشمند فقط پیشنهاد است؛ اعمال نهایی با تأیید منشی.

این تصمیم‌ها «قرارداد معماری» هستند و در توسعه‌های بعدی نباید با چند اسکریپت موازی یا DOM mutation شکسته شوند.

## 3. مدل دامنه

```text
Class
  └── Weekly Schedule
        └── Class Session (یک اجرای واقعی در یک تاریخ)
              └── Enrollment Session (وضعیت یک هنرجو در همان جلسه)
```

تغییرات روزانه روی `Class Session` انجام می‌شوند. تغییر برنامه هفتگی فقط با workflow صریح مدیریت برنامه انجام می‌شود.

### 3.1 تفاوت Reschedule و Make-up

- **Reschedule:** همان جلسه جابه‌جا می‌شود؛ شناسه جلسه حفظ می‌شود.
- **Make-up:** یک جلسه جدید برای جبران ایجاد می‌شود و به جلسه اصلی `original_session_id` متصل است.

این دو مفهوم نباید در UI یا Backend یکی فرض شوند.

## 4. لایه‌های UI

### لایه A — Header

- تاریخ شمسی و روز هفته
- ساعت زنده
- روز قبل / امروز / روز بعد
- بازخوانی و زمان آخرین همگام‌سازی

### لایه B — KPI عملیاتی

KPIها باید به جای شمارش‌های کم‌اهمیت، وضعیت واقعی عملیات را نشان دهند:

- جلسات امروز
- هنرجویان یکتا امروز
- حضور ثبت‌شده / در انتظار
- مبلغ قابل وصول امروز
- پرداخت‌های ثبت‌شده امروز
- موارد تمدید
- موارد نیازمند اقدام

**نکته:** تعداد «هنرجوی امروز» باید unique بر اساس `studentId` باشد، نه تعداد enrollment-sessionها.

### لایه C — Action Center / نیازمند اقدام

مرکز هشدار داشبورد است و باید قابل کلیک باشد. دسته‌ها:

1. حضور هنرجو ثبت نشده
2. حضور مدرس ثبت نشده
3. جلسه بدون اتاق
4. تعارض مدرس
5. تعارض اتاق
6. بدهی/صورتحساب معوق
7. پرداخت ناقص
8. تمدید نزدیک/لازم
9. جلسه لغوشده یا exceptionدار

هر آیتم باید به جلسه یا هنرجوی مرتبط قابل دسترسی باشد.

### لایه D — Timeline

- ستون برای هر اتاق فعال
- ستون `بدون اتاق` فقط در صورت وجود جلسه بدون اتاق
- خط NOW برای روز جاری
- نمایش جلسه جاری/بعدی/پایان‌یافته
- نمایش هشدار تعارض روی خود جلسه
- نمایش وضعیت حضور مدرس روی کارت

Timeline موجود بازنویسی نمی‌شود؛ فقط قابلیت‌های بالا به آن افزوده می‌شوند.

### لایه E — Session Operations

برای هر جلسه:

- مدرس
- ساعت و اتاق
- وضعیت جلسه
- حضور مدرس
- فهرست هنرجویان
- حضور هنرجویان
- وضعیت مالی
- تعداد جلسات مصرف‌شده/برنامه‌ریزی‌شده/باقی‌مانده
- وضعیت تمدید
- امکان ثبت پرداخت سریع
- امکان تمدید
- هشدارهای عملیاتی

### لایه F — Smart Planner

پیشنهاد زمان جایگزین و چینش هوشمند فعلی حفظ می‌شوند. Planner باید:

- پیشنهاد بدهد، نه اینکه بی‌اجازه تغییر دهد.
- Backend هنگام اعمال کل plan را دوباره اعتبارسنجی کند.
- conflictهای مدرس و اتاق را جداگانه بررسی کند.

### لایه G — پایان روز

در فاز بعد اضافه می‌شود:

- جلسات برگزارشده/لغوشده/جابجاشده
- حضور و غیبت
- پرداخت روز
- بدهی باز
- اقدامات باقی‌مانده
- Close Day

## 5. قوانین Conflict

تابع فعلی که فقط وقتی تعارض را تشخیص می‌دهد که **هم مدرس و هم اتاق یکی باشند** از نظر دامنه کافی نیست.

دو conflict مستقل داریم:

### Instructor Conflict

دو جلسه غیرلغوشده با یک `instructor_id` و زمان هم‌پوشان.

### Room Conflict

دو جلسه غیرلغوشده با یک `room_id` غیرnull و زمان هم‌پوشان.

یک جلسه می‌تواند هر دو conflict را هم‌زمان داشته باشد.

فرمول overlap:

```text
other.start < session.end
AND other.end > session.start
```

## 6. Session بدون اتاق

جلسه بدون اتاق صرفاً یک ستون fallback نیست؛ یک **هشدار عملیاتی** است.

اگر `room_id = null` باشد:

- در Action Center نمایش داده شود.
- روی کارت جلسه badge هشدار داشته باشد.
- در timeline ستون `بدون اتاق` قرار گیرد.

## 7. حضور

### هنرجو

وضعیت‌ها:

- pending = ثبت نشده
- present = حاضر
- absent = غایب
- excused = مرخصی
- withdrawn = انصراف

### مدرس

- pending = ثبت نشده
- present = حاضر
- absent = غایب

ثبت حضور باید کم‌کلیک باشد و بعد از ذخیره، state و همه نماهای مرتبط یک‌جا rerender شوند.

## 8. مصرف جلسات و تمدید

سه عدد باید از هم تفکیک شوند:

- consumed
- planned
- remaining

قانون فعلی مصرف: `present` و `absent` مصرف‌شده محسوب می‌شوند؛ `pending`، `excused` و `withdrawn` مصرف نمی‌شوند. این قانون باید در Backend به عنوان business rule صریح باقی بماند.

`renewalReady` یک business rule است و threshold فعلی آن `remaining <= 1` برای دوره‌های جلسه‌ای است. برای billing ماهانه نیز وضعیت تمدید باید بر اساس قواعد دوره/تاریخ بررسی شود، نه صرفاً یک badge ساده.

## 9. مالی

برای هر هنرجو:

- مبلغ صورتحساب
- پرداخت‌شده
- مانده
- تاریخ سررسید
- وضعیت: تسویه / ناقص / معوق / پرداخت‌نشده / بدون صورتحساب

در KPI روزانه باید از داده‌های موجود dashboard استفاده شود، اما در فاز مالی بعدی منبع حقیقت invoice/payment و قواعد refund/void نیز دقیقاً تعریف می‌شوند.

## 10. Cancellation و Exception

لغو باید در آینده دلیل ساختاری داشته باشد:

- غیبت مدرس
- غیبت هنرجو
- تعطیلی آموزشگاه
- مشکل فنی
- درخواست هنرجو
- درخواست مدرس
- سایر

`calendar_exception_type/title` باید در UI به صورت هشدار قابل تشخیص باشد.

## 11. Date / Timezone

تاریخ فعلی Client با timezone مرورگر ساخته می‌شود، در حالی که fallback API از UTC استفاده می‌کند. این اختلاف نزدیک نیمه‌شب می‌تواند روز اشتباه ایجاد کند.

راه‌حل معماری نهایی:

- timezone آموزشگاه به صورت یک setting صریح تعریف شود.
- تولید «امروز» در Client و Server از همان timezone انجام شود.
- تاریخ ذخیره‌شده در DB به شکل `YYYY-MM-DD` باقی بماند.

تا زمان پیاده‌سازی setting، تغییرات timezone باید با احتیاط و تست نزدیک نیمه‌شب انجام شوند.

## 12. Query و Performance

GET داشبورد فعلاً materialization روز و provisioning را نیز انجام می‌دهد و برای هر session یک query هنرجو اجرا می‌کند.

هدف معماری:

```text
GET dashboard = read-oriented
materialization/provisioning = explicit mutation/job
student data = batched/set-based query
```

به دلیل محدودیت quota در D1، این refactor بعد از تثبیت UX انجام می‌شود تا ریسک هم‌زمانی تغییرات کم بماند.

- جست‌وجوی هنرجو

## 17. اصول عدم شکستن معماری

هر قابلیت جدید باید این موارد را رعایت کند:

- یک source of truth
- یک render pipeline
- event delegation
- Backend validation
- no MutationObserver
- no duplicate DOM controllers
- تغییر روزانه روی Session، نه Schedule
- عملیات حساس قابل audit
- planner پیشنهاددهنده، نه تصمیم‌گیر خودکار

## 18. معیار پذیرش Phase 1

- «نیازمند اقدام» بدون reload وضعیت قابل فهمی بدهد.
- تعداد هنرجویان یکتا باشد.
- تعارض مدرس بدون تعارض اتاق نیز هشدار بدهد.
- تعارض اتاق بدون تعارض مدرس نیز هشدار بدهد.
- جلسه بدون اتاق قابل تشخیص و اقدام باشد.
- خط NOW فقط برای روز جاری نمایش داده شود.
- وضعیت مدرس روی timeline/session list دیده شود.
- KPIهای مالی و تمدید از همان داده state ساخته شوند و query اضافه غیرضروری به ازای هر کارت ایجاد نکنند.
- ساختار فعلی planner و attendance شکسته نشود.
